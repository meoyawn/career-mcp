# Rules

- Keep server instructions, tool descriptions, schemas and prompts focused on CRM operations, data semantics and API constraints. Job-search objectives, application strategy, effort budgets and approval policy belong to the calling workspace.
- Keep shared server instructions limited to cross-tool contracts; document operation-specific semantics in the relevant tool/schema and README. Context reads must serve the operation's required inputs. Optional metadata, enrichment and ranking must not become prerequisites for recording data; a successful mutation response confirms the saved state.
- Use `aube` only for package management and package commands. Never use `npm` or `npx`.
- Never create SQL triggers. Enforce stored invariants with CHECK, UNIQUE, and foreign-key constraints, and perform cross-row validation explicitly in the same transaction as the mutation. Preserve historical migrations; remove their active triggers with a forward migration.
- Each MCP tool call may execute at most one database transaction. Use one statement or one D1 batch for all validation reads, mutations, and returned data. Do not execute preliminary reads, follow-up reads, nested batches, or retries in separate transactions.
- Cover every migration with focused migration tests; a migration that drops/rebuilds tables or rewrites stored data must abort if its preservation checks fail. Code must pass `aube run check` before it deploys.
- **Never put secrets or private information in Git.** This includes active deployment URLs/hostnames, Cloudflare account and resource IDs, personal authentication profile names, credentials/tokens, applicant details, CV links, contacts, job-search records, and database/query exports. Treat deployment addresses and IDs as private even if a provider calls them public configuration.
- Keep deployment secrets outside the checkout in `~/.secrets/career-mcp/` (override with `CAREER_MCP_SECRETS`): `wrangler.deploy.jsonc` for the active deployment, optional `cloudflare.env` for `CLOUDFLARE_API_TOKEN`, optional `wrangler-profile` for a Wrangler auth profile. CI receives the same values as GitHub Actions secrets. Save private notes, imports, exports, and reports only under ignored `private/` or `backups/`. Confirm a private path is ignored with `git check-ignore` before writing it. Never force-add ignored files.
- Tracked `wrangler.jsonc` is local-only configuration with synthetic IDs. Documentation, examples, fixtures, generated types, and scripts must contain only placeholders or synthetic data; use localhost or reserved example domains for URLs. Never copy an active address or ID into this file, even to document what must remain secret.
- Deployments and remote database commands must go through `scripts/remote-wrangler.ts`, which uses the private deployment config and fails if it is missing. Local development, checks, tests, builds, and type generation must use the sanitized configuration and must not load deployment credentials.
- Before committing or pushing, inspect the complete staged diff and scan tracked content for secrets and private deployment/user data. Check generated files too. Do not print private values in shared logs, commit messages, PRs, or command arguments. Removing a value from current files does not erase Git history; check historical commits and report any remaining exposure.
- Deploy with `task deploy`. Pushes to `master` deploy through GitHub Actions with the same task.
